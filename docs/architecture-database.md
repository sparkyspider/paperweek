# Architecture: Database

**The WHAT** — the shape of persistence (lives in `back/`). Read this to understand it,
then follow `rules-database.md` (HOW). Why: `decisions-database.md`. Read
[`architecture-system.md`](architecture-system.md) first.

**KEEP TERSE.** A map. Structure once; constraints live in `rules-database.md`, signposted.

---

## Model

**PostgreSQL** (latest) + **Prisma 6** (ORM + migrations), TS strict. Schema in
`back/prisma/schema.prisma`; app data keyed by Zitadel `sub` (`ownerId`) — D-db-001.

## Databases (local dev = host Postgres, shared Zitadel with co-sy-v2)

Local dev uses the developer's host PostgreSQL. Two databases sit side by side:
- **`productivity-tools`** — this app's own data (this architecture — Prisma, no RLS).
- **`zitadel`** — the SAME Zitadel store co-sy-v2 uses: one shared local instance at
  `localhost:8080`, with a new "Productivity" org created inside it. We never touch it
  directly, only via its API/OIDC.

**Each service connects with its own login role** — never the `postgres` superuser at
runtime: role `zitadel` owns DB `zitadel`; role `productivity-tools` owns DB
`productivity-tools`. Passwords are autogenerated into env files.

## Entity catalog

The catalog itself lives as `///` doc comments on each Prisma model in
`back/prisma/schema.prisma` — that file is the source of truth for exact columns, and is
owned by the backend build. Expected shape, at a glance:

| Table   | Purpose |
|---------|---------|
| `theme` | A life-theme (e.g. "Health", "Work") — the grouping a backlog task hangs off. `owner_id` = Zitadel sub. |
| `task`  | A backlog or scheduled task, optionally under a `theme`. Carries `owner_id`, and once scheduled: which of the two visible weeks, which day (Mon–Sun), and which daypart (morning/afternoon/evening/notes). |

Table + column names are snake_case, `<domain>_<entity>` (drop the prefix when the
entity is the domain's own namesake — `rules-database.md` §Naming, D-db-010).

## Tenancy: per-user ownerId scoping, not Row-Level Security (D-db-016)

Unlike co-sy-v2's multi-org RLS model, productivity-tools has exactly one Zitadel
organisation. There is nothing to isolate at the organisation level — every user's data
must simply be invisible to every other user. That is enforced **in the service layer**,
not the database:

```
every owner-scoped query:   WHERE owner_id = <resolved user id>

resolved user id:           the verified JWT `sub` of the caller — OR, if the caller
                             holds the `agent` role, the user id named by a verified
                             X-On-Behalf-Of header (rules-roles.md, D-role-011)

                             no RLS, no FORCE ROW LEVEL SECURITY, no per-transaction
                             GUC — a normal Prisma query, always owner-filtered
```

This trades the database-enforced isolation co-sy-v2 relies on (a missing `WHERE` still
fails safe under RLS) for a much simpler model that fits a single-tenant-shaped app — the
cost is that the `ownerId` filter must never be forgotten in a query, since nothing
behind it will catch the mistake. See `rules-database.md` §Tenancy for the resulting
discipline (shared query helpers over ad-hoc `where` clauses).

## Migrations

`prisma migrate` only — never `db push`/auto-sync in shared or prod DBs.
