# Rules: Database

Applies to all DB work (lives in `back/`). Shape (WHAT): `architecture-database.md`.
Read `rules-system.md` and `decisions-database.md` first. **Keep terse.**

## Stack (fixed)
- **PostgreSQL (latest)** + **Prisma 6** (ORM + migrations). TS strict.
- npm; commit `package-lock.json`. Connection via env only — no committed secrets.
- **Per-service login roles — never the shared superuser at runtime.** Each service
  authenticates as its own role, owning only its own database: Zitadel → role `zitadel`
  (DB `zitadel` — the SAME shared local instance co-sy-v2 uses, just a new "Productivity"
  org inside it); our app's owner/migration role → `productivity-tools` (DB
  `productivity-tools`). Passwords are autogenerated (env locally). There is no RLS, so
  there is no separate non-owner runtime-role requirement — see Tenancy below.
- **Naming:** tables + columns are snake_case, `<domain>_<entity>` where useful; when the
  entity IS the domain's namesake, drop the prefix (`theme`, `task` — not `theme_theme`).
  Ownership is never encoded in a table name — the `owner_id` column carries it (D-db-016).
- Every Prisma model carries a `///` doc comment (the entity catalog; mirrored in
  `architecture-database.md`).

## Tenancy = per-user ownerId scoping, not RLS (D-db-016)
- There is a SINGLE Zitadel org ("Productivity"). Isolation is not between
  organisations — it is between USERS.
- `theme` and `task` (and any future user-owned table) carry `owner_id uuid NOT NULL`,
  set to the Zitadel JWT `sub` of the owning user.
- **Enforcement is at the service/query layer, not the database.** Every Prisma query
  against a user-owned table filters by `ownerId` — there is no Postgres RLS policy
  standing behind it. Prefer a shared repository/service helper that always injects
  `ownerId` over ad-hoc `where` clauses scattered across controllers/services, so a
  missed filter is structurally harder to write, not just a convention to remember.
- **`ownerId` has exactly one provenance:** the verified JWT `sub` of the acting caller
  — or, for a request carrying the `agent` role, the user id resolved from a verified
  `X-On-Behalf-Of` header (never trust that header from a non-agent caller). See
  `rules-roles.md` and `decisions-roles.md` D-role-011.
- **Never accept `ownerId`/`userId` as a client-supplied field on create/update.** It is
  always derived server-side from the token (or the on-behalf-of resolution), never read
  from the request body.

## Prisma specifics
- Standard Prisma Client — no RLS-related `SET LOCAL`/GUC binding, no interactive-
  transaction tenant context needed. A normal pooled connection is fine.
- Schema in `back/prisma/schema.prisma`. Map app data by Zitadel `sub` (`ownerId`).

## Migrations
- **Migrations only** (`prisma migrate`). Never `db push`/auto-sync in shared or prod DBs.
- Anything Prisma can't generate (custom indexes, functions) is authored as raw SQL
  inside a migration.

## Test data on a live database
- **Never run an `UPDATE` or `DELETE` without a `WHERE` clause.** A statement whose blast
  radius is "the whole table" is never the right tool, and no amount of care makes it
  safe to type on a machine holding real work.
- **Direct SQL is free on localhost, and gated everywhere else.** Test tooling may do
  whatever it likes against a database on localhost — disposable local stacks are for
  exactly that. The moment a connection string points anywhere not local, every direct
  `INSERT`/`UPDATE`/`DELETE` outside the app's own API or its migrations is a gated
  action — ask first, every time, and record it.
- Prefer, in order: going through the application (the same routes a user would);
  wrapping a proof in a transaction and rolling it back; deleting by primary key, one row
  at a time, naming each — over raw SQL cleanup on anything that isn't localhost.

## Don'ts
- No queries against `theme`/`task` (or any future owner-scoped table) that omit
  `ownerId` — there is no RLS guardrail behind you, so a missed filter is a direct
  cross-user data leak.
- No secrets in the repo; no owner/superuser DB creds in the app.
- No new top-level docs; keep DB rules changes inside this file.
