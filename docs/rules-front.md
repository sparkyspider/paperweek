# Rules: Frontend (`front/`)

Applies to everything under `front/`. Shape (WHAT): [`architecture-front.md`](architecture-front.md). Read [`rules-system.md`](rules-system.md) first.

## 1. Stack (fixed)

- **Nuxt 4** (latest stable) — the app framework.
- **TypeScript**, `strict: true`. No plain-JS source.
- **TailwindCSS v4** for all styling.
- Package manager: **npm** (the repo standard). Commit `package-lock.json`.
- **Approved libraries** (added past the fixed stack, each via a decision): **Pinia**
  (`@pinia/nuxt`, state — D-front-011); a drag-and-drop library for the week-grid
  interaction (chosen and recorded at D-front-029). No other UI/component library
  without a new decision that updates this list.

## 2. Project conventions

- Live entirely inside `front/`. Never reach outside it.
- Use Nuxt's directory conventions (`app/`, `pages/`, `components/`,
  `composables/`, `layouts/`, `server/`, etc.) as generated by Nuxt 4. Don't
  invent a parallel structure.
- Components are `PascalCase.vue`. Composables are `useThing.ts`.
- Use `<script setup lang="ts">` for all components.

## 3. Styling

- **Tailwind utilities first.** Avoid custom CSS; when unavoidable, keep it
  scoped to the component or in Tailwind's layer system.
- No other CSS framework or component library is added without a task that
  updates these rules.
- Design tokens (colors, spacing) go through Tailwind config, not magic values
  sprinkled in templates.
- **A colour token carries ONE meaning, and you may not borrow it.** Declare each
  token's meaning beside it in `app/assets/css/main.css` and show it on
  `/components/style-guide` → Colour. This project's palette is the art-paper /
  watercolor direction (D-front-029) — warm paper neutrals, ink for text, a small
  set of wash colours for the life-Themes, plus whatever functional colours (error,
  focus, agent-authored) the build needs. If a new signal doesn't fit an existing
  token, **add a token and document its meaning** — do not reach for the nearest
  hue that looks right. Reaching is how a signal stops being trustworthy.
- The design system is the single source of truth for the app: tokens live on the
  dev route `/components/style-guide`, components on `/components/ui`. Build from
  these, don't reinvent.

### Touch: a 44px floor, and it is not free (MUST)

Anything a finger taps is at least **44 × 44** under `@media (pointer: coarse)`. The floor is
declared **once, globally**, at the foot of `front/app/assets/css/main.css` — unlayered and last,
because the thing it must beat is a `h-7` or `py-2` utility sitting on the control itself. Do not
re-declare it per component, and do not reach for it on a desktop-only screen: a mouse never
matches `(pointer: coarse)`, and that is what keeps a phone fix from reflowing every screen.
This matters here specifically because the week-grid drag interaction is a prime touch surface —
dragging a task card between dayparts on a phone is a first-class use case, not an afterthought.

Four things to hold when you touch it, each of which cost co-sy-v2 a rework:

- **Grow the BOX, never the TYPE.** `min-height`/`min-width` open a control out around a label
  that keeps its own size — padding by another name. Reaching 44px by inflating a font changes the
  design while claiming to fix a target size.
- **`flex-shrink: 0` is part of the floor, not a tidy-up.** A flex item's default is
  `min-width: auto` — "never narrower than your own content" — and declaring `min-width: 44px`
  **replaces** it. Omit `flex-shrink: 0` and flex items squash their label instead of growing.
  Any rule that sets `min-width` on something inside a flex row carries it.
- **Growing a box is not the same as growing its hit area** — so prove the new pixels, don't
  measure them. A `getBoundingClientRect()` of 44 will happily be reported by an element whose
  listener still only covers the old, smaller area. **Tap the strip that exists only because of
  your rule** and confirm what it does.
- **Widen it by NAMING an element, never by widening the selector.** Bare `a` is excluded on
  purpose: a global link floor catches every link inside a sentence and pushes prose lines apart on
  a phone, which WCAG 2.5.8 exempts precisely because it is a worse trade. When a standalone
  navigational link genuinely needs the target, give it a class and a rule of its own. Do not
  "complete" the floor with `a { min-height: 44px }`.

Proving any of this is a **touch** context, not a screenshot: [§4](#4-building-anything-visual-must).

## 4. Building anything visual (MUST)

**Where to find components + live examples** (run `npm run dev`, port 3200). The
design-system hub is **`/components`** — nested-route tabs, deep-linkable:
`/components/style-guide` (tokens + raw vocabulary) · `/components/icons` (all icons) ·
`/components/ui` (basic UI primitives, with variants/states — each box has
**Preview / Code / API** tabs) · `/components/layout` (layout, incl. the `ModalShell`
frame) · `/components/functional` (reusable patterns — Alert/Confirm/Prompt/Wizard
modals) · `/components/dedicated` (feature one-offs, e.g. the WeekGrid and ThemeBacklog).
Read the code in `front/app/components/{ui,layout,functional,icons}/`; view it live on
those routes. Agents: check these **before** building — the example is on the route.
**Never hand-roll a modal** — compose `ModalShell` or a Functional modal (§5).

Before building **any** UI, in this order:
1. **Reuse an existing component** — check the **registries above** (`/components/ui`,
   `/components/icons`, `/components/functional`) first; never build what already exists (§5).
2. If none fits, **build a new component that follows the design system** — tokens
   from `app/assets/css/main.css`, patterns from `/components/style-guide`. No magic values, no
   off-system colours, no hand-rolled one-off styles.
3. If the system genuinely can't express the new UX mechanic, **update the style
   guide first** — add the token/pattern to `main.css` + `/components/style-guide` (and a
   component if it's reusable) — **then** build from it.

The design system is the **single source of truth** (`rules-system.md` §2):
read it in **code** — `main.css` (tokens), `app/components/` (components),
`/components/style-guide` (patterns) — and build from that. The rendered
`/components/style-guide` / `/components/ui` pages are the human catalogue + the
visual-verification target; the **code** is what you build from. Never re-describe
the visual spec in prose (it drifts); never bypass the system with ad-hoc styles.

**Viewing / verifying it live (how).** When you need to *see* the app — check a
screen renders, screenshot a route, confirm a flow — drive the running dev server
(`npm run dev`, port 3200) with a scripted browser (Playwright/Chromium, or the
`view-website` skill if set up for this repo) and check the screenshot + HTTP status
+ console errors. A front-end change passes visual verification on **HTTP 200 with
zero console/page errors** (D-front-013).

**Never prove a TOUCH property with a `fullPage` screenshot.** Playwright's
`screenshot({ fullPage: true })` re-issues `Emulation.setDeviceMetricsOverride` and
**silently drops `hasTouch` for the rest of the browser context**, so `(pointer:
coarse)` stops matching and every measurement taken after that first screenshot
quietly reads the pre-fix numbers. So, when what you are proving depends on touch:

1. Open the context with **`hasTouch: true`** — it is load-bearing, not decoration.
2. **Assert `matchMedia('(pointer: coarse)').matches === true` on every route, before you trust a
   single number**, and record the assertion beside the numbers.
3. Take **viewport-only** screenshots. A picture is not evidence of a touch property anyway; a
   live `getBoundingClientRect()` in a proven-coarse context is.

The general form — a reading is a claim about the instrument until you show it could have said
something else — is [`rules-agentic.md`](rules-agentic.md) §Prove the instrument before you
believe what it says.

## 5. Component taxonomy & feature modularisation

Six kinds of component. Keep them in separate homes — **never mix them**. The axes
are *how basic* (primitive → composed) and *how reusable* (generic → feature-specific).

| Kind | Does | Home | Naming |
|------|------|------|--------|
| **Icon** | One SVG glyph | `components/icons/` | `Icon*.vue` |
| **UI** | A **basic** primitive — button, field, badge, pill, chip, stepper | `components/ui/` | `PascalCase.vue` |
| **Layout** | Positions / centres / overlays; owns the **modal frame** | `components/layout/` (+ Nuxt `layouts/` for app chrome) | `PascalCase.vue` |
| **Functional** | A **reusable, composed pattern** with behaviour — Alert/Confirm/Prompt/Wizard modals, LoginBox | `components/functional/` (flat) | `PascalCase.vue` |
| **Dedicated** | A feature **one-off** — used once, wired to that feature's API (e.g. `WeekGrid`, `ThemeBacklog`, `TaskCard`) | `components/dedicated/<feature>/` | `PascalCase.vue` |
| **Page** | A routed screen | `pages/<feature>/…` (Nuxt autorouting) | route-named |

- **UI is basic.** Primitives/atoms — dumb, self-contained, reused everywhere. They
  don't compose features. A dialog is **not** UI (that's Functional); a `Button` is.
- **Every row/list action is a `Button`** — a worded act (Complete, Delete) is the
  design-system `Button`, and "quiet" is one of its VARIANTS, never a bare `<button>`
  styled as text.
- **Functional = reusable patterns.** Composed, behavioural, **one canonical each**
  (`ConfirmModal`, not five hand-rolled confirms). Feature-agnostic, so they stay
  **flat** in `components/functional/`. They compose UI + Layout.
- **Dedicated = feature one-offs.** Specific to one feature, used once there,
  **feature-sliced** (`components/dedicated/<feature>/`) and driven by that feature's
  store (§6). They compose UI, Layout and Functional patterns.
- **Registry scope (who appears in `/components`).**
  - **UI · Icon · Layout · Functional — MUST be fully registered:** every one appears
    in its gallery with variants/states (Functional shown in a representative context,
    since it's behavioural). These are the reusable vocabulary.
  - **Dedicated — only *mentioned*:** listed in the `/components/functional` (feature)
    registry in a representative context, **not** as a standalone catalogued widget.
    They're feature one-offs, not reusable vocabulary.
  - **Helpers — never registered:** private, single-use sub-parts sit in a `helpers/`
    subfolder next to their owner (see below).
- **Helpers = private sub-parts.** A sub-component broken out for clarity that will
  **never be reused elsewhere** lives in a `helpers/` subfolder beside its owner —
  most often `components/dedicated/<feature>/helpers/` (e.g. a drag-preview ghost node
  for `WeekGrid`), and also `components/functional/helpers/` for a Functional
  pattern's private support. The `helpers/` folder *is* the signal "private,
  single-use, skip the registry" (no QA/registry pass). Promote to UI/Functional and
  register it only if it later proves reusable. (Extends D-front-021.)
- **Feature-sliced.** Feature-specific code groups by feature — **one folder per
  discrete feature** (e.g. `week-grid`, `theme-backlog`, not a `planner/` bucket) —
  mirrored across `pages/`, `components/dedicated/`, `composables/`. UI, layout, icon
  and functional components are feature-agnostic and stay flat in their kind folder.
- **Explicit imports.** Import components explicitly; do **not** rely on Nuxt's
  flattened auto-import names.
- **JSDoc every component** — see [`rules-autodoc-logging.md`](rules-autodoc-logging.md) §1 (SSOT).
- **Layout owns positioning + the modal frame.** Centring, overlays and modals are
  layout. `ModalShell` is the **one** modal frame (fixed header, scrolling body,
  fixed footer). **Never hand-roll a modal** — compose `ModalShell`, or use a
  Functional Alert/Confirm/Prompt/Wizard modal. This is what stops every modal from
  drifting into its own thing.
- **Modals close deliberately — never on a backdrop click.** Clicking outside a modal
  does nothing; close is the ✕, Cancel/action buttons, or Esc. `ModalShell` has no
  backdrop-close opt-in prop and none may be added — an accidental click off the card
  must never throw away someone's half-filled Theme or Task form. A modal that
  overrides `#header` must therefore keep (or provide) a visible close control.
- **Dedicated components are agentic.** Dedicated components — **and only they** —
  export an agent-tooling descriptor (the other kinds only support; they perform no
  feature function). The descriptor points an agent at the API/swagger operations
  that back the component so it can be driven by intent ("move this task to Tuesday
  evening"). The contract, where built, follows **`rules-agentic.md` §2** (colocated
  `<Component>.agent.ts`, operationId refs, drive modes, generated registry). Don't
  hand-roll a divergent shape.

## 6. State management

- **Functional patterns are pure.** Being feature-agnostic, they take the model as
  **props** and emit **intent as events** — they **never** import a feature store,
  fetch, or hold domain state. UI-local state (open/closed, hover, inputs) stays local
  with `ref`; don't hoist it.
- **Dedicated components may bind the feature store directly.** Being feature-specific,
  a dedicated component MAY call `use<Feature>()` and bind it with `v-model` / call its
  actions, instead of threading every field through the page as props/events
  (D-front-018). It still holds **no** domain state of its own and never fetches — the
  store is the SSOT.
- **Domain state + actions live in a store.** A feature's model + actions live in a
  **Pinia setup store** (`stores/<feature>.ts`), shared across every screen of a flow
  (e.g. `stores/week.ts`, `stores/themes.ts`).
- **Pinia is the state library — not Vuex, not module-scoped mutable singletons**
  (those bleed across requests under SSR). Pinia (`@pinia/nuxt`) is SSR-safe and reads
  like a composable. See `decisions-front.md` D-front-011.
- **Shared-across-screens = one store instance.** When a flow spans screens, every
  screen uses the **same** store so they share one model.
- **Mock-first build:** a feature ships two stores with the **same shape** — `useXDemo`
  (model seeded from fixtures, actions mutate locally) and `useX` (calls the typed API
  layer, §7). Build and click through the UI against `useXDemo` with no backend; swap
  the import to `useX` to go live.
- **Types come from the model** — generate TS types from the backend's OpenAPI document
  (or a shared JSON Schema) so store, props, and API share one source of truth. No
  hand-kept parallel types.
- **The typed API layer (§7) is the only place HTTP happens.** Stores call it;
  components and pages never fetch directly.
- **Async status is data, not component state.** A request's pending/error status lives
  in the **store** (keyed by action/id) and is passed to components as **props** — they
  render it, never own it. Render it with the primitives, never a hand-rolled spinner:
  `Panel` `busy` (dim + `aria-busy` + overlay spinner) and `Button` `loading` (inline
  spinner + disabled). By blast radius: whole-model op → panel busy; single action →
  button spinner + panel dimmed as the double-submit guard. (D-front-016.)
  Four primitives, one family, on `/components/ui` under **Waiting — which of the
  four?**: **`Skeleton`** (content has not arrived and we know its shape — lists,
  the week grid on first load) · **`Panel busy`** (an operation over content that is
  already real — dims, goes `inert`, `aria-busy`, one centred spinner, and **holds its
  own footprint** so nothing jumps) · **`Button loading`** (one action in flight —
  label hides, spinner takes its place at the same width, click genuinely blocked) ·
  **`Spinner`** (the shared atom the other two are drawn from). All four still under
  `prefers-reduced-motion`. A fifth, hand-rolled anything is a rule breach.
- **Pessimistic for critical writes; never rubber-band.** Irreversible/critical writes
  (deleting a Theme with its backlog, completing a Task) update the model **only on
  server confirmation** — the button stays `loading`, nothing to revert. Optimistic
  updates are allowed only where the revert is cheap **and immediately, visibly**
  surfaced (inline error) — a **drag from backlog onto the week grid** is the natural
  place for optimism (snap back visibly on failure), since it's frequent, low-stakes
  and needs to feel instant. An action resolves at the end of its **visible** pending
  state; do not let the user proceed past an action whose outcome may retro-actively
  change. (D-front-016.)
- **The caller declares error-reporting ownership.** When a page invokes a store action
  off a component's intent event, it says who surfaces failure: centrally (the fetcher
  raises a global modal/toast) or returned for local/inline display —
  `modalOnError: boolean`, default `true` (`false` = error handed back to the caller).
  The fetcher logs centrally either way. (D-front-017.)

## 7. Talking to the backend

- All backend access goes through a single typed API layer (e.g. a composable /
  `$fetch` wrapper), configured via runtime config — **no hard-coded URLs** in
  components.
- The backend base URL comes from env (`NUXT_PUBLIC_API_BASE`, default
  `http://localhost:3201`), documented in `front/.env.example`.
- Never call the database or backend internals directly. HTTP only.

## 8. Auth

- Authentication is via Zitadel (OIDC), the shared local instance at
  `localhost:8080`, this project's own org ("Productivity"). The frontend is an
  OIDC client; it does **not** implement its own password storage.
- Tokens are handled per [`rules-auth.md`](rules-auth.md).

## 9. Quality gates

- `npm run build` (or `nuxt build`) succeeds.
- `npm run typecheck` (nuxi typecheck) passes with zero errors.
- Lint passes. Code is Prettier-formatted.
- No `console.log` left in committed code ([`rules-autodoc-logging.md`](rules-autodoc-logging.md) §3).
- **Visual check:** UI work is viewed live via a scripted browser — HTTP 200,
  zero console/page errors (§4, D-front-013).
- **Any asset we serve and never open is proven to PARSE before it ships** — every file in
  `front/public/` with a machine-readable format, `*.svg` first. One `xmllint`/Python parse per
  file; a failure names the file, the line and what the parser could not read. (co-sy-v2 shipped
  a favicon with an illegal double-hyphen inside an XML comment that rendered nothing in any
  browser for a week while every build stayed green and every request answered 200 — a green
  build and an HTTP 200 prove DELIVERY, never VALIDITY.)

## 10. Don'ts

- No new top-level docs.
- No committing `.env`, `.nuxt/`, `node_modules/`, or build output.
- No pulling backend/auth source into the frontend.

## 11. App shell & need-to-know nav (page-guard)

The authed surface (`/app/**`) is a **role-gated app shell** whose menu is **derived from the
pages**, not hand-authored (D-front-022). The role model here is deliberately small — this is a
single-org, per-user app, so it's `user` and `agent` (rules-users.md), not co-sy-v2's tier
ladder — but the derivation mechanism is the same and is worth keeping:

- **The PAGE declares LINK → PAGE → RIGHT** in `definePageMeta`: `requiredRole` (a Zitadel role
  string), `navLabel` (the LINK; omit ⇒ page still reachable but **not** in the menu), `navIcon`
  (icon component **name**, a string — page-meta must serialise), `navOrder` (sort key), and
  `layout: 'app'`.
- **The LINK is derived.** `useAppNav()` walks `router.getRoutes()` and returns a sidebar item
  **only if** it has a `navLabel` **and** a `requiredRole` **and** `auth.hasRole(requiredRole)`. No
  `requiredRole` ⇒ **no menu item** (deny-by-default) — visibility must reflect *actual* access.
- **The PAGE is guarded**, not just hidden. The `auth` middleware, after the session check, bounces
  away when `to.meta.requiredRole` is set and `!auth.hasRole(...)`.
- **Front-hiding is UX, not security.** The back independently guards the same right on that page's
  endpoints — never rely on the hidden menu. Keep the two in lockstep.
- **The PAGE also declares its browser-tab NAME**, in the same `definePageMeta`, as `title` — and
  only the short half: `title: 'This Week'`, never `'Productivity Tools — This Week'`. `app/app.vue`
  holds the one `titleTemplate` that adds the brand half once, so it cannot drift page to page.
  Never `useHead({ title })` in a page: a page's name is a static fact about the ROUTE.

## 12. Copy (MUST)

Product copy is written from **what the person meant**, never from what the code does. The two
read the same to whoever wrote the feature and completely differently to whoever uses it.

- **Never describe a constraint as a choice.** If the product left the person no alternative,
  the sentence says so. The reliable tell is a sentence that begins **"You have…"** about
  behaviour the product imposed — it credits the user with a decision they were never offered.
  A theme that auto-carries incomplete tasks into next week is a system behaviour, not something
  "you chose" — say what happened, not what they decided.
- **Never offer a remedy that does not exist.** A dead instruction costs more than no instruction:
  the reader assumes they failed to find it.
- **Never promise the unbuilt.** State only what is true now. "Soon you will be able to…" is a
  commitment with a date attached to it, in a place nobody will remember to revisit.
- **A control's label says what the control changes — nothing wider.** If a label needs a second
  correction, the **control**, not its wording, is the problem.

## 13. Deep links must always land (MUST)

**The requirement, stated before any mechanism: a direct URL must serve the app.** Somebody
typing an address, opening a bookmark, hitting refresh, or reopening a shared link to a specific
week days later must get a working page — whether or not that route was ever pre-rendered, and
whether or not the routing table currently knows the path. The front end, not the server,
decides what a URL means.

**Two ways this requirement is met — different mechanisms, identical constraint:**

1. **As served today** — Nitro, with `routeRules: { '/app/**': { ssr: false } }` in
   `front/nuxt.config.ts`. That rule IS the SPA fallback: any path under `/app` gets the app
   shell back. It is not an oversight and must not be removed or narrowed.
2. **If the front end were ever served statically** — no Nitro process at all — the identical
   requirement lands on the **web server**: every unmatched path must be rewritten to
   `index.html`, or a deep link dies at the edge before a line of our code runs. See
   [`rules-deployment.md`](rules-deployment.md).

**Why it outranks a correct status code.** The server would have to assemble a signed-in
person's data (this week's themes and tasks) before anyone has proven who they are, which
`ssr: false` avoids entirely — and caching a rendered authed page is the direct route to serving
one person another's screen. A hard load of `/app/<nonsense>` answers **200** with the shell,
and then `app/error.vue` renders the not-found stage client-side — a **plastic 404**: it reads
and behaves as a not-found to the person while the status stays 200 for the machine. Routes
**outside** `/app` are server-rendered and keep their genuine HTTP 404 (also dressed by
`error.vue`); only `/app` carries the deep-link promise.

## 14. Day-strip wheel scrolling (MUST)

Shape: `architecture-front.md` §Day-strip wheel scrolling; why: D-front-030…037.

- **Never compare raw wheel deltas — rate only** (px/tick from `WheelEvent.timeStamp`). OS timestamps alternate 16/33 ms; raw deltas sawtooth.
- **No CSS `scroll-snap` on the strip**, not even `proximity`.
- **Ambient dock listeners (`scrollend`, scroll-debounce) stay gated while a wheel gesture is owned** (`wheelGestureActive`).
- **One plan per touch.** Solve in `handleFingerRelease` only; a red "PING xN" on the HUD is a defect, not noise.
- **Every change to `wheelIntent.ts`, `dockPhysics.ts` or DayStrip's scroll code** passes `npm run test:unit` (both spec files) AND the Playwright rig in BOTH engines — `docs/process/evidence/scroll-diagnosis-2026-09-03/after3/rig/trackpad-rig.mjs`, including the recorded-stream (sawtooth) replay.
- **Feel changes are not "done" on synthetic evidence.** Mark's hand on the live recorder (`OPERATIONS.md` §12) decides; his verdict is recorded verbatim before anything further moves.
